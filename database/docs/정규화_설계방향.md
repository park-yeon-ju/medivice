# 메디바이스 데이터 정규화 및 DB 설계 방향

> 작성자 : 박기준 (DA) · 작성일 : 2026-09-02
> 관련 산출물 : `sql/01_schema_ddl.sql`, `dbml/광주2_○조_메디바이스-DB.dbml`, `src/normalize.py`

## 1. 데이터 출처 정의

메디바이스의 데이터는 성격이 전혀 다른 두 갈래에서 들어온다. 설계의 첫 결정은 이 둘을 어떻게 나누고 어디서 만나게 할 것인가였다.

| 레이어 | 출처 | 성격 | 갱신 주기 |
|---|---|---|---|
| **Layer A · 참조 데이터** | 식약처 공공 API 4종 (아래) | 서비스는 읽기만 한다 | 배치 (주 1회 등) |
| **Layer B · 서비스 데이터** | 사용자의 등록·기록 행위 | 런타임 CRUD | 실시간 |

수집 대상 API는 다음 4종이다. 하나가 하나의 테이블군을 채운다.

| 공공데이터포털 ID | API | 채우는 테이블 |
|---|---|---|
| 15059486 | 의약품안전사용서비스(DUR) 품목정보 — 오퍼레이션 6종 | `dur_types`, `dur_pair_rules`, `dur_single_rules`, `ingredient_daily_limits` |
| 15056780 | 의약품안전사용서비스(DUR) 성분정보 — 병용금기 | `ingredients`, `dur_pair_rules` |
| 15095677 | 의약품 제품 허가정보 | `products`, `manufacturers`, **`product_ingredients`(성분·함량)** |
| 15075057 | 의약품개요정보(e약은요) | `product_infos` |

이 중 **15095677이 없으면 파이프라인이 조용히 무너진다.** DUR 응답은 품목에 어떤 성분이 들어 있는지는 알려주지만 **1정당 함량은 주지 않는다.** 함량이 없으면 `일일 투여량 = 함량 × 1회 투여량 × 1일 횟수`가 `NULL`이 되고, 그 약은 합산에서 빠져 **판정 대상에서 조용히 제외된다.** 초안에서 제품명을 정규식으로 긁어 함량을 추정했으나("○○정 500mg" → 500), 제품명에 함량이 없는 품목에서는 실패한다. 허가정보의 `MATERIAL_NAME` 필드가 이 자리를 메운다.

```
총량 : 1정 중-|성분명 : 아세트아미노펜|분량 : 500|단위 : 밀리그램|규격 : KP|비고 : ;
```

복합제는 이 묶음이 `;`로 이어져 오므로, 이것 자체가 **1NF 위반이며 파싱 시 행으로 쪼갠다.**

두 레이어는 **`ingredients`(성분) 하나로만 만난다.** 사용자가 등록한 약(`medications`)을 성분 단위로 펼쳐(`product_ingredients`) DUR 규칙(`dur_pair_rules` / `dur_single_rules`)에 대조하는 경로가 곧 UC15(성분 충돌 판정) → UC16(메디라이트) 실행 경로다. 성분 코드를 조인 축으로 잡은 것이 이 설계의 중심 결정이다.

## 2. 원본 데이터의 문제 — 왜 정규화가 필요한가

식약처 DUR 병용금기 API는 아래처럼 한 행에 모든 것이 붙어 있는 **플랫한 한 장짜리 표**로 응답한다.

```
ITEM_SEQ | ITEM_NAME | ENTP_NAME | INGR_CODE | INGR_KOR_NAME | MIXTURE_ITEM_SEQ | MIXTURE_INGR_CODE | ... | PROHBT_CONTENT
```

이 표에는 네 가지 문제가 숨어 있다.

| # | 문제 | 위반하는 정규형 | 실제로 생기는 이상 |
|---|---|---|---|
| ① | 같은 품목이 금기 쌍 개수만큼 반복되어 제품명·업체명이 계속 중복된다 | 2NF | **갱신 이상** — 업체명이 바뀌면 그 업체의 모든 행을 고쳐야 한다 |
| ② | `INGR_CODE`를 알면 `INGR_KOR_NAME`이 따라온다 | 3NF | **이행 종속** — 성분명 표기가 개정되면 수만 행을 동시에 고쳐야 한다 |
| ③ | 복합제의 성분이 한 칸에 묶여 들어온다 | 1NF | **성분 단위 합산 불가** — UC15의 "일일 합산량" 자체를 계산할 수 없다 |
| ④ | `(A,B)`와 `(B,A)`가 모두 내려온다 | — | **완전 중복** — 규칙 건수가 정확히 2배가 되고, 판정 결과도 두 번 뜬다 |

③이 특히 중요하다. 메디라이트의 핵심 기능인 "아세트아미노펜이 두 제품에 겹칩니다"는 **성분이 행 단위로 펼쳐져 있어야만** `SUM()`으로 계산된다. 정규화는 여기서 미관의 문제가 아니라 **기능의 전제**다.

## 3. 정규화 단계별 적용

### 3-1. 1NF — 한 칸에 하나의 값

- 복합제의 성분 목록을 `product_ingredients` 교차 테이블의 **행**으로 펼쳤다.
- 금기 쌍의 좌(`ITEM_*`)와 우(`MIXTURE_*`)를 각각 독립된 품목·성분 개체로 분리했다.

### 3-2. 2NF — 다른 주체의 정보는 따로 뺀다

원본 한 행에 섞여 있던 컬럼을 "무엇에 대한 정보인가"로 갈랐다.

| 원본 컬럼 | 무엇에 대한 정보인가 | 분리한 테이블 |
|---|---|---|
| `ENTP_NAME` | 제조사 | `manufacturers` |
| `ITEM_SEQ`, `ITEM_NAME`, `CHART` | 품목 | `products` |
| `INGR_CODE`, `INGR_KOR_NAME` | 성분 | `ingredients` |
| `PROHBT_CONTENT`, `NOTIFICATION_DATE` | 금기 규칙 | `dur_pair_rules` / `dur_single_rules` |
| `efcyQesitm` 등 e약은요 텍스트 | 품목 상세(1:1) | `product_infos` |

### 3-3. 3NF — 정보가 정보를 낳지 않게 한다

- `INGR_CODE → INGR_KOR_NAME` 이행 종속을 끊고, 사실 테이블에는 `ingredient_id`만 남겼다.
- `TYPE_NAME`('병용금기', '임부금기'…)이 매 행 반복되던 것을 `dur_types` 코드 테이블로 뺐다. `severity` 컬럼이 여기 붙어 있어 **메디라이트 색 결정 규칙이 코드 테이블 조회만으로 끝난다.**
- 같은 이유로 서비스 데이터 쪽에서도 진료과(`departments`)와 부작용 증상(`symptoms`)을 코드 테이블로 분리했다.

### 3-4. 정규화만으로 풀리지 않는 문제 — ④ 양방향 중복

정규형 규칙으로는 `(A,B)`와 `(B,A)`를 걸러낼 수 없다. **제약조건으로 푼다.**

```sql
CONSTRAINT chk_pair_order CHECK (ingredient_a_id < ingredient_b_id)
```

항상 작은 id가 왼쪽에 오게 강제하면 한 쌍은 물리적으로 한 행만 가질 수 있다. 조회할 때는 `LEAST` / `GREATEST`로 같은 규칙에 맞춰 찾는다.

```sql
JOIN dur_pair_rules r
  ON r.ingredient_a_id = LEAST   (a.ingredient_id, b.ingredient_id)
 AND r.ingredient_b_id = GREATEST(a.ingredient_id, b.ingredient_id)
```

성분 단위 병용금기 1,836행을 전량 정규화하면 1,292개 고유 성분 쌍으로 접힌다.
품목 단위 797,186행은 같은 성분 규칙이 품목 조합만큼 반복되므로 20,000행 계통표본만 유지한다.
적재 후 "양방향 중복으로 남은 쌍 = 0"을 확인했다.

## 4. 키 및 제약조건 설계 방향

- **기본키(PK)** — 전 테이블 `GENERATED ALWAYS AS IDENTITY` 대체키를 쓴다. 식약처 품목기준코드(`item_seq`)와 성분코드(`ingr_code`)는 자연키이지만 **UNIQUE 제약으로만 관리**한다. 공공데이터 코드 체계는 개편되며, 자연키를 PK로 쓰면 그때 FK 구조 전체가 흔들린다.
- **외래키(FK) 및 삭제 정책**
  - `products.manufacturer_id → manufacturers` : `ON DELETE SET NULL`. 업체 정보가 정리되어도 품목 데이터 자체는 보존되어야 한다.
  - `product_ingredients`, `medication_ingredients` : `ON DELETE CASCADE`. 부모가 사라지면 성분 연결은 의미를 잃는다.
  - `medications.product_id → products` : `ON DELETE SET NULL`. 마스터에서 품목이 빠져도 사용자의 복용 기록은 남아야 한다.
  - `side_effect_snapshots.medication_id` : `ON DELETE SET NULL` + **제품명·성분을 값으로 복사**. UC14로 약을 지워도 부작용 기록은 그대로 읽혀야 하므로, 참조는 끊되 표시용 텍스트는 스냅샷으로 보존한다.
- **CHECK 제약** — 업무 규칙을 DB 층에서 강제한다.
  - `side_effect_logs.occurred_date <= CURRENT_DATE` : 미래 날짜 선택 불가(예외 흐름)
  - `medications` : `product_id IS NOT NULL OR custom_name IS NOT NULL` — 수기 등록(UC13)이라도 이름은 반드시 있어야 리스트에 표시된다
  - `family_links.from_user_id <> to_user_id` : 자기 자신과의 가족 연동 방지
- **N:M 교차 테이블 4종** — `product_ingredients`, `user_allergies`, `side_effect_symptoms`, `family_links`(자기참조). 모두 복합 PK로 중복 등록을 원천 차단했다.
- **컬럼을 만들지 않는 것도 설계다** — 주민등록번호 컬럼은 존재하지 않는다. 판정에 쓰이는 것은 연령과 성별뿐이고, 연령은 `birth_date`에서 계산된다. "쓰이지 않는 정보는 받지 않는다"는 수집 원칙을 스키마 층에서 지킨다.

## 5. 설계 검증 — 스키마가 판정을 실제로 지탱하는가

`sql/03_medilight_views.sql`의 뷰 5종으로 UC15 → UC16 경로를 구현하고, 설계 문서의 메인 화면 예시를 그대로 데이터로 넣어 확인했다.

| 복용 항목 | 성분 | 1회 함량 × 1일 3회 | 일일 투여량 |
|---|---|---|---|
| ○○정 500mg (처방약) | 아세트아미노펜 | 500mg × 3 | 1,500mg |
| ○○ 종합감기약 325mg | 아세트아미노펜 | 325mg × 3 | 975mg |
| 부루펜정 200mg | 이부프로펜 | 200mg × 3 | 600mg |
| ○○ 종합감기약 (복합제 2성분) | 클로르페니라민말레산염 | 2.5mg × 3 | 7.5mg |

함량은 전부 `MATERIAL_NAME`에서 파싱했고(확보율 100%), 종합감기약은 복합제라 성분 2행으로 분해되었다.

판정 결과 : 아세트아미노펜이 **2개 제품에 겹치고** 합산 2,475mg (상한 4,000mg) → **YELLOW**, 최종 메디라이트 = `YELLOW`. 설계 문서의 "주의 — 아세트아미노펜이 두 제품에 겹칩니다"가 데이터로 재현되었다.

> 검증 과정에서 결함을 하나 고쳤다. 초안의 `v_overdose`는 "상한의 80% 근접"만 노랑 조건으로 걸어 두어, **상한에 여유가 있는 성분 중복을 놓쳤다.** 설계 문서는 "같은 성분이 두 제품에 있거나 상한에 근접했다"를 노랑으로 정의하므로, `COUNT(DISTINCT medication_id) >= 2` 조건을 OR로 추가했다. 또 상한 데이터가 아직 수집되지 않은 성분에서도 중복은 잡아야 하므로 `ingredient_daily_limits`를 `LEFT JOIN`으로 바꾸었다.

## 6. 초록과 '확인하지 못함'을 구분한다

검증 과정에서 더 중요한 문제를 하나 발견했다. 종합감기약의 **클로르페니라민말레산염**은 DUR 응답에 등장하지 않아 성분코드가 없다. 이런 성분은 어떤 규칙에도, 어떤 상한에도 걸리지 않으므로 판정 로직을 그냥 통과한다. 그 결과 화면에는 **초록**이 뜬다.

그런데 설계 문서상 초록의 뜻은 *"확인된 문제 없음"* 이다. 실제로는 *"확인하지 못했음"* 인데 같은 색으로 보인다. **복약 안전 서비스에서 가장 위험한 실패 방식이다** — 사용자는 안전하다고 읽고 넘어간다.

`v_uncovered_ingredients` 뷰로 이를 드러냈다. 복용 중인 성분 가운데 DUR 규칙에도, 쌍 규칙에도, 일일 상한에도 없는 것을 골라낸다. 성분코드가 `LOCAL_` 로 시작하는 것은 공공 데이터에서 매칭되지 않아 내부적으로 부여한 코드이며, 그 자체가 판정 근거 없음의 표시다.

색 체계는 3색 그대로 두었다. 네 번째 색을 만들면 화면 설계가 흔들리기 때문이다. 대신 `v_medilight`에
`uncovered_count`와 `amount_missing_count`를 함께 반환하고, `v_safety_notice`가 사용자에게 출력할 문장을 완성한다.
프론트에는 `v_medilight_api`가 이를 `OK/WARN/CRIT`로 변환해 제공한다.

**이 문장은 AI가 생성하지 않는다.** AI에 맡기면 "큰 문제는 없어 보입니다" 같은 완화된 표현이 나올 수 있고, 안전 고지는 문장이 흔들리면 안 된다. 색을 규칙 엔진이 정하는 것과 같은 이유다. 그래서 문구를 `notice_templates` 테이블에 **언어별 행으로** 저장하고 성분명만 치환한다 — UC27 한/영 전환이 있으므로 문구를 코드에 하드코딩하면 두 벌을 관리해야 하고, 이는 그 자체로 갱신 이상을 만든다. 문구도 정규화 대상이다.

```
복용 목록의 성분 중 1개는 안전성 판정에 필요한 공공 데이터가 없어 확인하지 못했습니다:
클로르페니라민말레산염. 문제가 없다는 뜻이 아니라 확인하지 못했다는 뜻이므로,
해당 성분에 대해서는 의사 또는 약사와 상담하시기 바랍니다.
```

이 변경은 Use-Case 층까지 올라간다. `docs/UseCase_수정안.md`에 UC31(신규) 및 UC16·UC17·UC27 변경분을 정리했다.

## 7. 정리

본 설계는 (1) 공공 API 3종 원본의 1NF~3NF 위반을 단계별로 해소하고, (2) 정규형으로 풀 수 없는 양방향 중복을 CHECK 제약으로 처리했으며, (3) 자연키와 대체키를 분리해 외부 코드 체계 변경에 대비했고, (4) 화면에 보이는 모든 값이 테이블 컬럼으로 추적되도록(trace-through) 구성했으며, (5) 판정하지 못한 성분을 판정 결과와 구분해 드러냈다. 정규화의 목적은 표를 예쁘게 쪼개는 것이 아니라, **메디라이트 판정이라는 서비스의 핵심 기능이 SQL 한 줄로 성립하게 만드는 것**이었다.
