표 29개와 선 37개가 왜 그 자리에 있는지, 그리고 “약을 등록하면 왜 색이 바뀌는지”를 데이터 흐름 순서대로 따라가는 노트. 발표 전에 이 순서대로 읽으면 그대로 설명이 된다.

데이터가 지나는 4칸

DB는 “데이터를 담는 곳”이 아니라 이 파이프라인의 세 번째 칸이다. 앞뒤를 같이 말해야 설명이 끊기지 않는다.

1 · 수집식약처 공공 APIJSON 230,809행을 data/raw/에 그대로 저장
2 · 정규화파이썬 → CSV중복을 접고 표 10개로 분해, 148,664행
3 · 적재PostgreSQL표 29개에 넣고 FK로 연결 · 여기가 ERD
4 · 판정뷰 10개SELECT 한 번으로 GREEN/YELLOW/RED

ERD는 3번 칸의 설계도다. 그래서 ERD를 설명한다는 건 “어떤 표를 만들었는가”가 아니라 “이 표들이 4번 칸의 판정을 어떻게 가능하게 하는가”를 말하는 것이다. 표 하나하나를 훑으면 청중은 지루해하고, 판정 경로를 따라가면 설계 의도가 드러난다.

한 문장 요약. 왼쪽은 식약처에서 받아온 바꾸지 않는 참조 데이터, 오른쪽은 사용자가 만드는 서비스 데이터, 그 둘이 만나는 유일한 지점이 ingredients(성분)다.

ERD 기호는 결국 4개뿐

ERD를 처음 보면 선이 많아 보이지만, 실제로 쓰이는 개념은 네 가지다. 우리 표로 하나씩 짚으면 외울 것이 없다.

기호뜻우리 DB의 예
PK 그 표에서 행 하나를 콕 집는 번호. 중복될 수 없다. products 의 product_id — 품목 43,019개에 붙은 일련번호
FK 다른 표의 PK를 가리키는 칸. “이 행은 저기 소속”이라는 뜻. products.manufacturer_id → manufacturers — 제조사 이름을 매번 적지 않는다
1 — N 부모 하나에 자식 여럿. 화살표는 자식이 부모를 가리킨다. 사용자 1명 → 복용 중인 약 여러 개 (users 1 : N medications)
N : M 양쪽 다 여럿. 표 사이에 교차 테이블을 하나 끼워 푼다. 약 하나에 성분 여럿, 성분 하나가 약 여럿에 → product_ingredients 92,355행

ERD의 색도 그냥 예쁘라고 칠한 게 아니라 이 네 가지에 대응한다. 파랑은 공공 API에서 받아 읽기만 하는 참조 데이터, 초록은 사용자가 만드는 서비스 데이터, 주황은 N:M을 푼 교차 테이블, 보라는 반복되는 문자열을 빼낸 코드 테이블이다. 발표에서 “주황 상자가 다대다를 푼 자리, 보라 상자가 중복 문자열을 뺀 자리” 한 줄이면 정규화 설명이 끝난다.

왜 굳이 성분 단위로 쪼갰나

정규화는 “보기 좋으라고”가 아니라 기능이 성립하려면 어쩔 수 없어서 했다. 이 대비가 발표의 핵심 근거다.

식약처 병용금기 API는 품목 조합으로 내려온다. 같은 금기 규칙 하나가 “A약 × B약”, “A약 × B′약”… 조합 수만큼 반복되어 797,186행이 된다. 이걸 그대로 저장하면 표가 커질 뿐 아니라, 신약이 하나 나올 때마다 행이 또 불어난다.

보관 방식행 수새 약이 등록되면
품목 조합 그대로797,186조합 수만큼 행이 늘어난다
성분 쌍으로 접기1,292규칙은 그대로, 약만 성분에 연결하면 끝

성분 쌍으로 접으면 규칙은 1,292개로 줄고, 새 약은 product_ingredients에 성분만 연결하면 자동으로 판정 대상이 된다. 이것이 ingredients가 ERD 한가운데에 놓인 이유다 — 모든 조인이 성분을 축으로 지나간다.

정직하게 말할 부분. 함량은 92,355행 중 66,748행(72%)만 확보했다. 나머지는 식약처 원본의 QNT 값 자체가 비었거나 적량·범위처럼 숫자가 아니다. 추측해서 채우지 않고 NULL로 두고, 화면에 “함량 미상”을 표시한다. 안전 서비스에서 추정값은 없는 값보다 위험하다.

판정 6단계 — “약을 등록하면 왜 색이 바뀌나”

여기가 발표의 본론이다. 판정경로 ERD를 띄우고 왼쪽에서 오른쪽으로 이 순서대로 읽으면 된다. 번호는 실제 실행 순서다.

1

사용자가 약을 등록한다

처방약·영양제·상비약이 모두 한 표에 들어간다. 처방약이라고 판정에서 빼지 않는다.

medications
2

약을 성분으로 펼친다

식약처 품목이면 마스터에서, 수기 등록이면 직접 입력분에서 성분을 꺼낸다. 복합제 1품목이 성분 N행으로 펼쳐지는 지점 — 1NF를 지킨 덕분에 가능하다.

product_ingredients또는 medication_ingredients
3

성분을 조인 축으로 모은다

이 사용자가 오늘 먹는 성분 목록과 하루 합산량이 만들어진다. 단위가 g·mcg면 여기서 mg로 환산한다. 농도를 모르는 mL는 환산하지 않고 남긴다.

ingredients→ v_active_ingredients
4

규칙 4종과 대조한다

상한 초과 · 병용금기 · 단일금기(임부·연령·용량주의) · 효능군 중복을 각각 확인한다. 네 가지가 서로 다른 표를 보지만 전부 성분 축에서 만난다.

ingredient_daily_limits dur_pair_rules dur_single_rules ingredient_effect_groups
5

걸린 항목만 근거와 함께 저장한다

어떤 성분이 왜 걸렸는지, 합산량과 임계값이 얼마였는지, 어느 고시가 근거인지 (source_ref·rule_version)까지 남긴다. 나중에 “왜 빨간불이냐”에 답할 수 있어야 한다.

safety_check_items
6

가장 심한 항목이 최종 색이 된다

항목 중 하나라도 RED면 RED, 아니면 YELLOW, 둘 다 없으면 GREEN. 프론트에는 OK / WARN / CRIT로 바꿔 넘긴다.

safety_checks→ v_medilight→v_medilight_api
GREEN → OK걸린 규칙 없음. 단, “안전”이 아니라 “확인된 문제 없음”이다.
YELLOW → WARN성분·효능군 중복, 또는 상한의 80% 이상.
RED → CRIT상한 초과 또는 병용금기. 전문가 확인이 필요하다는 신호.
여기서 한 설계 판단. 판정 근거가 아예 없는 성분(영양제 등)을 초록으로 숨기지 않는다. uncovered_count와 amount_missing_count로 따로 세어 화면에 문구로 붙인다. 사용자가 “확인 못 함”을 “이상 없음”으로 읽는 것이 안전 서비스의 가장 위험한 실패이기 때문이다.

뷰(VIEW)는 “이름 붙여 저장해 둔 SELECT”다

표(TABLE)와 뷰(VIEW)의 차이 한 줄: 표는 데이터를 갖고 있고, 뷰는 갖고 있지 않다.

뷰는 데이터를 복사해 두는 게 아니라 질문을 저장한다. SELECT * FROM v_medilight를 실행하는 순간 저장돼 있던 SELECT문이 그 자리에서 돌아 지금 시점의 표를 읽어 결과를 만든다. 그래서 약을 하나 추가하면 뷰를 고치지 않아도 다음 조회에서 색이 바뀐다.

우리가 뷰를 쓴 이유는 세 가지다. ① 판정 로직이 백엔드 코드가 아니라 DB 안에 있어 프론트·AI가 같은 답을 본다. ② 복잡한 조인을 한 번만 써 두고 이름으로 부른다. ③ 스키마가 실제로 판정을 지탱하는지 증명이 된다 — 설계가 말뿐이 아니라는 근거다.

-- 최종 색을 정하는 뷰의 핵심 (sql/03_medilight_views.sql)
CREATE OR REPLACE VIEW medivice.v_medilight AS
SELECT u.user_id,
       CASE MAX(CASE x.level WHEN 'RED' THEN 3 WHEN 'YELLOW' THEN 2 END)
            WHEN 3 THEN 'RED' WHEN 2 THEN 'YELLOW' ELSE 'GREEN'
       END AS medilight_level
  FROM medivice.users u
  LEFT JOIN ( -- 규칙 4종의 결과를 한 줄로 쌓는다
        SELECT user_id, level FROM medivice.v_overdose
        UNION ALL SELECT user_id, level FROM medivice.v_pair_conflict
        UNION ALL SELECT user_id, level FROM medivice.v_effect_dup
        UNION ALL SELECT user_id, level FROM medivice.v_single_conflict
       ) x ON x.user_id = u.user_id
 GROUP BY u.user_id;

읽는 법: “사용자별로(GROUP BY), 규칙 4종에서 나온 판정 중 가장 심한 것(MAX)을 최종 색으로 삼는다.” 이 한 문장이 뷰 전체의 뜻이다.

SQL은 5문장이면 우리 판정이 읽힌다

함수를 다 알 필요가 없다. 아래 다섯 개가 우리 뷰의 99%다.

문장하는 일우리 쿼리에서
SELECT … FROM어느 표에서 어떤 칸을 꺼낼지“복용 중인 약을 꺼낸다”
JOIN … ON두 표를 공통 칸으로 이어 붙인다 ON pi.product_id = m.product_id — 약과 성분을 잇는 바로 그 선(FK)
WHERE행을 걸러낸다WHERE m.ended_at IS NULL — 아직 복용 중인 것만
GROUP BY같은 값끼리 묶는다“성분별로 묶어라”
SUM() · MAX()묶인 것들을 하나의 숫자로 SUM(daily_amount) — 하루 합산량. 중복 판정이 여기서 나온다

중요한 연결. SUM()이 성립하려면 성분이 행 단위로 펼쳐져 있어야 한다. 복합제 성분이 한 칸에 "아세트아미노펜, 카페인"처럼 묶여 있으면 합계를 낼 수 없다. “정규화를 왜 했나”의 답이 바로 이것이다 — SUM() 한 줄이 성립하게 하려고.

-- 성분 중복 판정의 뼈대
SELECT ingredient_id, COUNT(*) AS 겹친제품수, SUM(daily_amount) AS 합산량
  FROM v_active_ingredients
 WHERE user_id = 1
 GROUP BY ingredient_id
HAVING COUNT(*) > 1;   -- 두 제품 이상에 같은 성분이면 YELLOW

sql 폴더의 파일 9개 — 무엇을, 왜 그 순서로

“SQL 파일을 실행한다”는 건 그 안에 적힌 문장을 위에서부터 DB에 보낸다는 뜻이다. 번호는 반드시 지켜야 하는 의존 순서다 — 표가 없으면 뷰를 못 만들고, 뷰가 없으면 판정을 못 한다.

파일하는 일왜 이 순서인가
01_schema_ddl표 29개를 만든다 (CREATE TABLE)모든 것의 바닥
02_seed_code코드 값(DUR 유형·진료과·증상)과 인덱스표가 있어야 값을 넣는다
03_medilight_views판정 뷰 10개표와 데이터가 있어야 조회가 성립
04_demo_scenario실데이터로 RED·YELLOW·안내문구를 실제로 출력설계가 작동한다는 증빙
05_unit_conversion_check400mg + 0.7g = 1,100mg → RED 검사단위 환산이 맞는지
06_schema_alignment기존 DB에 부족한 칸만 추가데이터를 지우지 않는 이관용
07_alignment_check함량 미상 경고·API 상태 매핑 회귀 검사고친 뒤에도 여전히 맞는지
08_widen_name_columns품목명 칸을 300 → 500자로 확장전량 적재 때 391자 품목명이 나와서
09_fix_single_rule_uniqueness재적재 시 규칙이 2배로 늘던 문제 수정NULL은 서로 같지 않다는 SQL 규칙 때문

실행하는 두 가지 방법

# psql 이 PATH 에 있을 때
psql -h localhost -U postgres -d medivice_db -f sql/04_demo_scenario.sql

# psql 없이 파이썬으로 (윈도우에서 PATH 문제를 피하는 쪽)
python src\setup_db.py --all
알아두면 설명이 깔끔해지는 것 — 트랜잭션. 05와 07은 BEGIN으로 시작해 ROLLBACK으로 끝난다. 가짜 사용자와 가짜 약을 넣어 판정이 제대로 도는지 확인한 다음 전부 없던 일로 되돌린다. 그래서 검사를 몇 번 돌려도 실제 DB는 더러워지지 않는다. “검사용 데이터는 커밋하지 않는다”는 한 줄로 설명하면 된다.

이런 질문이 들어온다

실제로 나올 법한 것만 골랐다. 답은 한두 문장으로 끊는 게 낫다.

표를 왜 29개나 만들었나요? 하나로 하면 안 되나요?

한 표에 넣으면 같은 값이 계속 반복되고, 값 하나 바뀔 때 여러 행을 동시에 고쳐야 해서 어긋납니다. 더 결정적인 건 합산이 안 된다는 점입니다. 성분이 한 칸에 묶여 있으면 SUM()을 못 써서 “같은 성분이 겹치는지”를 계산할 수 없습니다.

병용금기 79만 건 중 2만 건만 받았다는 게 표본 아닌가요?

판정의 기준은 성분 단위 API(1,836행 전량)입니다. 79만 건짜리는 같은 규칙이 품목 조합만큼 반복된 것이라, 전량을 받아도 규칙은 늘지 않습니다. 2만 건은 원본 구조 검증과 제품 예시용으로 전 구간 계통추출한 것이고, 앞에서부터 자르면 규칙 7종만 잡히는 편향이 있어 간격을 두고 뽑았습니다.

함량이 28% 비어 있는데 판정이 신뢰할 만한가요?

비어 있는 건 저희가 못 채운 게 아니라 식약처 원본의 QNT가 비었거나 ‘적량’ 같은 문자열인 경우입니다. 임의로 숫자를 넣지 않고 NULL로 두었고, 그 성분은 합산에서 빼되 화면에 “함량 정보가 없어 합산하지 못했다”고 명시합니다. 숨기는 것보다 드러내는 쪽이 안전합니다.

판정 로직을 왜 백엔드가 아니라 DB(뷰)에 넣었나요?

같은 판정을 프론트·AI 설명·보고서가 각각 다시 구현하면 답이 갈라집니다. 뷰 하나를 기준으로 두면 어디서 조회해도 같은 색이 나오고, 규칙이 바뀌었을 때 고칠 자리도 한 군데입니다.

ERD의 ingredients가 가운데 있는 이유가 있나요?

참조 데이터와 서비스 데이터가 만나는 유일한 접점이기 때문입니다. 약(서비스)도 성분으로 펼쳐지고, 금기 규칙(참조)도 성분에 붙어 있어서 모든 판정 조인이 이 표를 지나갑니다. 그림에서 가운데 둔 것도 그 뜻입니다.

처방받은 약인데 경고가 뜨면 의사가 틀렸다는 건가요?

아닙니다. 경고는 처방 오류 단정이 아니라 전문가 확인이 필요하다는 신호입니다. 그래서 처방약도 판정에서 제외하지 않고, 안내 문구도 AI가 생성하지 않는 고정 템플릿으로 씁니다. 표현이 완화되거나 과장되면 안 되기 때문입니다.
