정규화의 목적을 ‘미관’이 아니라 ‘기능 요건’으로 재정의

정규화
상황
병용금기 응답이 797,186건. 단순히 “크다”가 아니라, 같은 금기 규칙이 해당 품목 조합 수만큼 반복 폭발한 구조였다. 게다가 복합제 성분이 한 칸에 묶여 와 1NF를 위반하고 있었다.
판단
이 서비스의 핵심 기능인 “같은 성분이 여러 약에 겹치는지”는 성분이 행 단위로 펼쳐져 있어야만 SUM()으로 계산된다. 정규화를 보기 좋으라고 하는 게 아니라, 판정 기능이 SQL 한 줄로 성립하게 만드는 전제로 규정했다.
결과
품목 조합을 성분 쌍으로 접고, 성분을 조인 축으로 삼는 스키마 확립. 이후 모든 판정 로직이 이 축 위에서 동작.

실데이터를 열어 설계 초안의 스키마 결함을 발견·재설계

스키마
상황
초안은 ‘효능군중복’을 성분 쌍으로 모델링했다. 그러나 실제 API 응답을 열어보니 MIXTURE_* 필드가 아예 없고, EFFECT_NAME·SERS_NAME — 즉 ‘성분→효능군 분류’였다. 쌍으로 파싱하면 규칙이 0건이 된다.
판단
중복 여부는 데이터가 알려주는 게 아니라 판정 시점에 계산해야 하는 것이라고 판단. 문서상 정의가 아니라 원본 실데이터를 근거로 스키마를 다시 잡았다.
결과
effect_groups + N:M 교차 테이블 신설, 판정 뷰가 “복용 성분들의 효능군이 겹치면 경고”를 계산. 효능군 9종·매핑 256건 확보.

데이터 소스와 판정 규칙의 불일치를 간파하고, ‘모르는 것’을 드러내는 설계

데이터 정합성
상황
영양제·건기식 성분은 식약처 DUR 고시 대상이 아니라, API를 추가로 받아와도 대조할 판정 규칙 자체가 없다. “데이터를 더 넣으면 된다”는 접근이 통하지 않는 지점이었다.
판단
무작정 소스를 늘리는 대신 성분 중심 스키마로 출처와 무관하게 판정되도록 설계. 더 중요하게는, 판정 근거가 없는 성분을 ‘초록(안전)’으로 숨기면 안 된다고 봤다 — 사용자가 “확인 못 함”을 “이상 없음”으로 읽는 것이 안전 서비스의 가장 위험한 실패다.
결과
판정 불가 성분을 별도 집계하는 뷰 + 상담 권고 안내(UC31) 도입. 안내 문구는 완화 표현이 섞이지 않도록 AI가 아닌 결정론적 템플릿으로 고정.

일일 호출 한도 vs 79만 건 — 편향 없는 계통추출로 수집 설계

수집 전략
상황
개발계정 한도는 일 1,000회. 79만 건을 100건씩 받으면 8천 회로 한참 초과. 게다가 앞에서부터 자르면 응답이 DUR_SEQ 순 정렬이라 규칙 7종만 잡히는 편향이 있었다 — “머리부터 N건”은 표본이 아니었다.
판단
전 구간을 일정 간격으로 건너뛰는 계통추출(systematic sampling)로 전환. 서버 페이지 크기를 실측하고, 실행 전 예상 호출량을 미리 계산해 한도 초과를 사전 차단.
결과
한도 내에서 전 구간에 고르게 분포한 규칙 수집. 중단 시 이어받기(--resume)로 호출 낭비 방지.

“실패해도 200을 주는” 공공 API를 결정론적으로 검증

수집 견고성
상황
공공데이터포털은 개편 때마다 엔드포인트 버전 접미사(…03, …06)가 바뀌고, 인증·경로가 틀려도 HTTP 200에 오류코드를 실어 보낸다. 죽은 엔드포인트가 정상처럼 통과하기 쉬웠다.
판단
후보 URL을 나열하고, HTTP 상태·resultCode·totalCount까지 함께 확인해 실제로 살아있는 경로만 자동 확정하도록 진단 단계를 분리. 자연키/대체키를 분리해 코드 체계가 개편돼도 FK가 흔들리지 않게 설계.
결과
확정 엔드포인트를 endpoints.json에 기록 → 경로를 손으로 고칠 일 없음. 실데이터 검증에서 병용금기가 실제 판정으로 이어짐: RED · 심바스타틴 × 이트라코나졸 (횡문근융해증)

“목록 API에 함량이 없다” — 같은 데이터셋의 다른 오퍼레이션을 찾아 72%까지 보강

함량 커버리지
상황
일일 상한 합산은 함량이 있어야만 성립하는데, 제품 허가정보 목록 응답(getDrugPrdtPrmsnInq07)에는 MATERIAL_NAME이 없었다. 기존 서비스 범위 21,093건 중 7,999건이 함량 미상이라 그만큼 판정이 스킵됐다.
판단
품목별 상세 조회는 42,984회 호출이 필요해 한도를 넘는다. 공식 Swagger 명세를 열어 같은 데이터셋 안의 주성분 상세 오퍼레이션(getDrugPrdtMcpnDtlInq07, 126,768행)을 찾아냈다. numOfRows=1000은 resultCode 11로 거부돼 500으로 실측 조정, 254회로 전량 수집했다.
결과
기존 누락 7,999건 중 5,310건(66%)을 공식 데이터로 보강. 전체 함량 확보 66,748 / 92,355(72%).

QNT='250,500,1000,1500' — 쉼표를 천단위로 읽으면 250억이 된다

파싱 안전
상황
적재 중 numeric field overflow. 추적해 보니 혈액응고인자 제제의 QNT가 하나의 값이 아니라 규격 목록(250·500·1000·1500 IU)이었다. 쉼표를 지우던 파서가 이를 25,050,010,001,500이라는 존재하지 않는 함량으로 만들었다.
판단
천단위 구분자(1,250.5)와 규격 목록은 자릿수 패턴으로 구분된다. 목록·범위·적량 같은 비정형 값은 임의로 하나를 고르지 않고 NULL(=모름)로 남기기로 했다 — 안전 판정에서 추정값은 없는 값보다 위험하다.
결과
parse_qnt() 도입 후 최대 함량이 18,000,000 IU(알데스류킨 주사제)로 정상화. 남은 NULL 25,607건은 원천 QNT 공백·비정형이며 경고 뷰로 정직하게 노출한다.

정직한 한계. DUR 용량주의 API에는 1일 최대용량 수치 필드가 없어, 성분별 임계값은 공공 API만으로 완결되지 않는다(텍스트 추출 + 큐레이션 병행). 임계값이 없는 성분은 판정 뷰가 중복 자체만으로 경고를 띄우도록 설계해 결손을 흡수했다.
